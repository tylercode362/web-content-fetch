# Design

## Ownership

```text
web-content-fetch
  UI / JobStore / Queue / Orchestrator / Progress / EPUB writer

chrome-bridge
  Pairing endpoint / real Chrome tab / site adapter / lazy-load / asset evidence
```

web-content-first 是 job truth。chrome-bridge 是 browser evidence provider，不保存整部作品的長期 queue。

## Prior-art analysis

- `epub-scheduler-older/main/background.ts` 提供的是 queue、lock、retry 與暫存清理；沒有 Kobo 圖片尺寸、inline `width`／`height` 或 KEPUB 轉換，所以這些責任放在 WCF writer 與固定的 `kepubify` stage。
- 舊漫畫 crawler 使用 headless HCCrawler、固定 `#mangaBox img` 與 response interception；對本次目標頁不可靠：頁面實際使用 `#manga`／`#panel`，初始 DOM 沒有主要 `<img>`，以 `#pageNo` 與 `a[data-action="next"]` 的頁面內動作切換 200 頁，並夾有廣告容器與第三方廣告腳本。
- 舊 Linovel flow 偏向網站專用 HTTP／HTML 解析；新流程讓真實 Chrome 處理登入、lazy-load、蓋板與頁面狀態，再只把章節與可驗證 asset evidence 交給 WCF。這保留既有 Browser Read 邊界，不把 cookie 或整個 Chrome profile 複製到服務。
- `opendata-research` 的可移植做法採用於本設計：Docker／Compose 是權威環境、固定 digest、non-root／read-only／resource bounds、tools 執行時無網路、依賴授權盤點、RED→GREEN→REFACTOR→VERIFY，以及對 partial／blocked／recovered 狀態保留可見診斷。

## Flow

```text
Task UI
  -> DownloadJobStore
  -> DownloadQueue
  -> Bridge session
  -> discover chapters
  -> fetch one chapter and follow next
  -> verified content/assets
  -> novel book EPUB OR manga chapter EPUB
  -> fixed kepubify v4.0.4 -> matching .kepub.epub output
  -> persisted progress + same-origin SSE event
```

## Job output

- Novel: one input work produces one EPUB; each chapter is one ordered XHTML spine item.
- Manga: one input work produces one EPUB per chapter; each page is a separate image/XHTML asset with inline numeric dimensions. Each EPUB also produces a matching `.kepub.epub` through the pinned open-source `kepubify` binary; the original EPUB is retained.

## Pairing

The UI configures a Bridge URL, accepts only a one-time six-digit code generated by the Extension, exchanges it once, and stores only the resulting revocable service binding. Neither Local Bridge nor NAS Bridge exposes a no-code or environment-variable pairing shortcut. The code is never a long-lived bearer secret and is never included in logs or URLs.

The runtime image creates `/var/lib/web-content-fetch/state` and `/var/lib/web-content-fetch/output` with the non-root app ownership before Compose mounts the named volumes. This keeps persisted pairing state and generated files writable without running the application as root.

## API boundary

The companion Bridge protocol is versioned and additive. The first additive operation is authenticated `content.fetch`, exposed by the Bridge service client as `contentFetch(browserClientId, body)`. It has two modes:

- `chapters`: open a work page and return same-work chapter URLs.
- `chapter`: open one chapter, follow same-work next/下一頁 links within a bounded session, and return either sanitized-by-the-consumer novel HTML fragments or ordered manga image evidence.

The current Bridge response includes image URL, natural width, natural height and source page. Image bytes remain an explicit asset stage in web-content-fetch; the service MUST verify the response content type, size and digest before placing bytes in EPUB.

## Callback and failure policy

- The callback URL is configured separately from the Bridge URL and MUST be reachable from the Bridge runtime; loopback callback URLs are rejected. Callback authentication uses a per-job token and job id. The callback endpoint accepts progress only and never accepts content bytes or credentials.

- Unsupported URL: reject before opening a tab.
- Pairing failure: no content operation.
- Missing or undecoded image: retry within budget, then fail closed.
- Image lazy-loading is handled in the real tab with bounded scrolling, `currentSrc`, declared lazy attributes and `HTMLImageElement.decode()`; a URL alone is not proof that bytes were loaded.
- The current implementation does not use unrestricted DevTools/webRequest response interception. That is an evaluated fallback only for a site whose browser-visible image request cannot be verified through the allowed content adapter.
- Unresolved overlay or ambiguous next state: `needs_user_action` or failed, never silent success.
- For action-based pagination, the adapter clicks only the site-declared `nextActionSelector`, waits for a page signature change, deduplicates image URLs, and stops at the bounded page limit. It does not treat a stale image or unchanged page as progress.
- SSE/EventSource loss: reload persisted snapshot and continue from idempotent job state.
